# RSVP 작동 가정 오프라인 감사 — 2026-09-12 23:46 KST

사용자 요청에 따라 현재 저장된 trace/phase/guidance와 Sacred config/info를 분석했다.
완료 dense 336/337와 sparse 324/325는 각각 첫1M, 진행 soft RSVP 346/347은 공통
첫400k를 사용했다. 총 **4,800,000개 훈련 스텝**, 6개 실행이다. 새 환경·LLM 호출·
학습은 하지 않았고 실행 중 프로세스와 학습 코드를 변경하지 않았다.

## 결론

**CUSUM은 발화한다. 그러나 현재 자료는 '지침이 낡아서 갱신이 유익한 시점을 고른다'는
주장을 검증하지 못한다.** 발급 때의 양의 가치 게이트가 열리면 대부분 곧 갱신하고,
닫히면200스텝을 기다리는 두 종류의 유지 시간이 나타난다. 새 출력은 대부분 달라지지만
실행 불가능한 목표가 반복되며, 크리틱의 별도 데이터 예측력과 갱신의 인과 이득은 미측정이다.

## 2. 発給時に閉じたゲートを途中で開き直していない

runnerは発給時に`_v_ref=None`へ戻し、trusted headと正の基準値の条件を通過したとき
だけ値を設定する。次の発給まではその条件を再判定しない。低価値状態で発給された
後に交戦へ移っても、途中で監視が有効になる設計ではない。

発給診断の主な拒否理由は`low_vref`。dense seed0/1で57.2%/68.9%、softで
61.4%/62.7%、sparseで69.7%/70.7%。`no_heads`は0.8–2.6%なので、ライブラリ
解決失敗やwarmupが主因ではない。low_vrefはbase<.001とvr<.25*baseの合算であり、
低い正値・負値・小さいbaseの内訳は既存ログから分離できない。

この6実行は`h=3`, `k=.6`, `min_interval=10`, `sched_target_early_per_ep=0`で、
**hの予算適応は無効**。過去のh適応あり実験と同じ設定として説明しない。

検出対象のgamma=.8は実効的に約5ステップ、25ステップ先の割引重みは約.0038。
これは近い将来のpredicate発生量を強く反映し、200ステップにわたる戦略の適切さ
そのものではない。価値の減少は交戦終了や敵の撃破でも起き得る。

## 3. 学習失敗と監視範囲縮小が同時に起きる

dense seed1の0–200k→800k–1Mで、armedス テップ比率は5.5%→2.3%、early/10kは
25.4→11.35となった。同期間のログ区間平均でshaping非零率は.514→.099に低下し、
critic_lossは.465→.219とむしろ下がる。

対してdense seed0はarmedが4.7%→14.6%、early/10kが21.8→36.85へ増加する。
失敗してpredicateが発生しなくなると推定値が低くなり、ゲートも閉じるという内生的な
連動と整合する。ただし因果の方向はこの相関では確定しない。

**lossが下がったことは予測器の成功ではない。** 非零信号が減ると学習問題も変化する。

## 4. 発火は終盤に偏るが、それだけではない

phaseログはpost-step状態キーなので現在tより厳密に前の値を用い、発給時には保存された
現在cache_keyを使った。比較はt_ep>0、armed、ratioあり、since>=10の判断可能ス テップに
限定。episode末尾5ス テップ以内は終了近接proxyであり死亡/敗北ラベルではない。

| 実行 | early時の終了5step以内 | eligible非発火時 | 粗い条件合わせ後の非発火比較 |
|---|---:|---:|---:|
| dense s0 | 10.5% | 4.1% | 7.6%（対応early10.4%） |
| dense s1 | 15.3% | 7.3% | 11.3%（対応early15.3%） |
| soft s0 | 13.4% | 4.2% | 10.9%（対応early13.5%） |
| soft s1 | 13.4% | 4.7% | 9.3%（対応early13.4%） |

条件合わせは学習200k区間、아군生存数、敵可視有無、発給から25step区分、episode内
10step区分。発火数で非発火率を再重み付けした記述統計で、無作為比較や有意差検定ではない。
発火が後続のepisode長を変えた可能性もあるため、この終端proxyで検出精度を主張しない。

denseの単独生存時の発火割合は18.4%/14.3%、比較非発火ス テップは5.5%/6.7%。
終盤・戦力低下に偏るが、**発火の大半が敗北直前というわけではない**。sparseの
終了近接差は小さく、denseの傾向を全環境へ一般化しない。

dense earlyの14.2%/18.0%は発給元が前のepisodeにある。国面内の劣化とepisodeを
またいだ参照の違いも分けて追う必要がある。これは失敗原因の確定ではない。

## 5. 新しい出力は変わるが、無効目標を除去できていない

同一predicate/typeのweightを合算したベクトルで比較すると、early更新の97.5–98.5%、
通常の上限更新の98.2–98.8%で値が変化する。したがって「同じ答えが返るだけ」ではない。
ただしこれは係数ベクトルの変化であり、実軌道での報酬変化や性能改善ではない。
またearlyで特に大きな変化が起きるという明確な傾向もない。

**earlyで更新した直後でも**、아군単独生存時に新指針がfocus_fireを含む件数は：

- dense s0: 347/563 =61.6%、s1:212/289 =73.4%。
- soft s0:131/196 =66.8%、s1:109/180 =60.6%。

focus_fireは二人以上の攻撃者が必要なので、その時点では実行不可能。
スケジューラが新しい出力を取得しても、この種の不適合を修復できていない。
将来episode reset後に再度有効になる可能性はあるため、生涯無効とまでは言わない。

## 6. 現ログで検証できない二点

### 크리틱の別データ予測精度

`ValueCritic.trusted()`は`head_var>1e-4`を見るだけで、R²や予測誤差は見ていない。
`critic_loss`は現在の学習bufferから抽出したminibatchの標準化MSEの移動平均。
したがって低loss、trusted=Trueのどちらも別episodeでの予測精度を保証しない。

現在のtraceにはhead別prediction、実F_j、MC target、x、head集合が保存されておらず、
critic重みも通常のactor/mixerチェックポイントにない。既存の別環境GRF bot-policyの
LOO結果を現在のSMACオンラインcriticの検証として代用できない。現実験のR²/MAEは
**算出不能**とする。

### 更新した場合と維持した場合の外部return差

同一状態からの分岐や非更新対照軌道がないので因果効果は計算できない。
更新後に勝率が上がるか、更新前後にvが回復するかだけでは代替できない。特にvの
基準は更新時に再設定され、回復の一部は定義上生じる。

## 7. 次に追加すべき最小の検証

1. 次の診断ランで各episodeの**更新前predictionと実predicate列**を保存し、その
   episodeをcriticに入れる前にMC targetとの誤差を測る（prequential評価）。全headと
   実際にゲートで採用したheadを分け、無条件平均baselineとのR²/MAEを報告する。
   base/vr/採用head比率も発給ごとに保存し、low_vrefの内訳を分ける。
2. 低価値でゲートを閉じた区間の状態遷移を確認し、**途中で監視を再開する必要**を検証する。
   比率の小分母問題を避ける現在のガードには理由があるので、検証なしに削除しない。
3. 'ゲートが開いたら短周期、閉じたら200'の対照と、同じ呼出予算のfixed/randomを
   比較する。現在のCUSUMがゲートと簡単なタイマー以上の価値を持つかを分離する。
4. 更新vs維持は別途分岐実験が必要。soft経路なら固定政策で行動介入、shaping-onlyなら
   同じ短い学習更新を含めて比較する。原シミュレータ状態・RNGの復元可能性を事前検証する。

現時点での判定は**「検出実装は動作、適切なタイミングの選択と更新の効用は未検証、
現在の設定には監視の空白と出力品質の問題がある」**。アイデア全体の否定でも成功宣言でもない。
