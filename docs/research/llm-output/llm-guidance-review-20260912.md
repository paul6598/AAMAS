# LLM 지침 직접 검토 — 2026-09-12

사용자 요청으로 [기존 출력 예시 16개](llm-guidance-examples-20260912.md)를 모두 읽고,
[pipeline smoke 문서](llm-pipeline-smoke-20260912.md)와 그 JSON의 실제 요청·응답·
availability·컴파일된 마스크를 대조했다. 학습 수치와 현재 실행 상태는
[실험 원장 §8am](../archive/experiments-log.md)에 기록했다. 새 학습·LLM 호출이나 학습 코드 수정은 없다.

## 판단

현재 LLM은 병종과 생존 수에 반응하는 전략 문장을 만들지만, 그 전략의 조건과 순서를
실행 가능한 보상/행동에 충실히 옮기지 못한다. 특히 카이팅·후퇴·탱킹이 상시 방향 이동이나
피해 패널티로 축약된다. 따라서 JSON 성공과 문장의 그럴듯함만으로 지침의 효용을 평가할
수 없다. 스케줄러는 이 지침을 언제 교체할지 바꾸므로, 부적절한 실행 의미를 스스로
복구한다고 기대하기 어렵다.

과거 문서의 16개는 원 API 응답이 아니라 sanitizer 이후 출력이다. 입력 원문도 없으므로
방향 선택이 당시 관측과 맞았는지, 누락이 LLM과 sanitizer 중 어디서 발생했는지는 대체로
확정할 수 없다. 상황별로 선정된 표본이라 오류율의 모집단 추정도 아니다.

16개 모두 forbid가 비어 있다. 현재 표본의 주된 문제를 과거의 전면 hard 금지로 설명하면
안 된다. enemy_kill은 16/16, focus_fire는 13/16으로 반복된다. 전략 문장에 비해 실제
보상 선택은 공통 메뉴의 가중치 조정에 가깝지만, 이 표본만으로 상태 의존성이 없다고
결론내리지는 않는다.

단독 생존 사례 03/07/11/12/15 중 4개에 실행 불가능한 focus_fire가 있다. 이는 그
순간의 무효 항목이다. 지침이 다음 에피소드까지 유지되면 새 아군 수에서는 다시 활성화될
수 있으므로, 지침 전체 수명에 걸쳐 항상 0이라는 주장은 아니다.

## 소프트 편향이 실제로 하는 일

현재 compiler는 겹친 선호를 더하지 않고 최대 weight로 합친다. controller는
Q + β log(weight)를 이용한다. 공격과 이동에 같은 weight를 주면 둘 사이의 Q 차이는
그대로다. 이것만으로 공격 후 후퇴라는 순서가 생기지 않는다.

β=.1, weight=2이면 +.0693이다. 여러 다른 행동에 같은 양을 더하는 것은 전략적 순서를
지정하는 것과 다르다. 실제 argmax 변경량은 각 상태의 Q gap과 availability를 함께 봐야 한다.
선호는 명령이나 확률이 아니며, 마스킹 RSVP 신규 팔은 훈련에서만 soft 편향을 적용한다.
따라서 그 팔의 평가 성능은 편향 없이 학습된 정책이 얼마나 유지되는지를 보여 준다.

## pipeline smoke: 입력이 있어서 더 확실하게 판정 가능한 사례

실제 한 에피소드의 step0/2/30/51을 paper와 paper_v2에 각각 한 번 호출한 총8개 응답이다.
8개 모두 HTTP200/finish_reason=stop이고 캐시 off다. 반복 실험이나 정책 학습 비교는 아니다.

1. **step0, 적 미관측:** paper_v2는 subgoals=[]와 북쪽 이동만 반환한다. 불필요한
   보상 항목을 비운 점은 개선 후보지만 북쪽을 선택할 관측 근거는 없다. 탐색 행동으로
   방향 하나를 택하는 것은 가능하므로 곧바로 사실 환각이라고 하지는 않는다. 다만 200
   step까지 재사용할 지침으로 적절한지는 별도 문제다. shaping-only 팔에서는 이 출력이
   셰이핑 0이 되므로 prompt 교체가 초기 학습 신호를 없애는 효과도 생긴다.
2. **step2, 적 관측·사거리 밖:** 두 버전 모두 공격 선호만 준다. 저장된 availability와
   soft를 교차하면 다섯 아군 모두 실행 가능한 선호 행동 수가 0이다. 공격 선호가 있다는
   것만으로 접근이 유도되는 것이 아니다. 이 시점의 action intervention은 없다. 문서의
   '다수 아군 교전' 표제보다 실제 summary의 approaching/out-of-range를 기준으로 해석한다.
3. **step30, 아군 Zealot 전멸:** paper는 'lone Zealot 보호'를 말하고 protect_type(Zealot)을
   발급한다. 입력 summary는 아군 Zealot 0/3 alive를 명시하므로 확실한 상태 해석 오류다.
   적 쪽에는 Zealot 한 명이 보인다. 진영을 혼동했을 가능성이 있지만 내부 원인은 단정하지
   않는다. paper_v2는 아군 Zealot 보호를 제거하고 적 Stalker 공격으로 일치시켰다.
4. **step51, HP2%의 마지막 Stalker:** paper는 다시 focus_fire를 넣는다. paper_v2는 이를
   제거하고 서쪽 후퇴를 제안한다. 적이 동쪽이라는 입력과는 일치한다. 다만 protect_type의
   원 weight가1.5여서 sanitizer가1.0으로 잘랐다. 낮은 체력에서 적 피해와 자기 사망의
   절충이 승리에 유리한 보상인지까지 이 출력만으로 보장할 수 없다.

**paper_v2의 새 문제:** 4개 중3개 응답에서 subgoal weight가 허용 범위[0,1]을 벗어난다.
step2의 kill_type/protect_type=1.5, step30의 kill_type=1.5/damage_type=2.5,
step51의 protect_type=1.5다. sanitizer가 전부1로 바꿔 유효 JSON만 보면 이 실패가 숨는다.
predicate 배율과 priority weight를 혼동했을 가능성이 있으나 확정 원인은 아니다.

입력 token 합은 paper=3,643, paper_v2=6,631로 약1.82배다. completion token 합은
1,362→1,507이며 총 token은5,005→8,138(약1.63배)다. 단일8호출 표본이라 일반적인
비용 증가율은 아니며, 토큰에서 wall-clock 또는 과금 비용을 그대로 추정하지 않는다.

따라서 paper_v2는 상태/활성 조건 오류를 일부 개선한 **검증 후보**다. 아직 성공한
프롬프트가 아니다. 과거16개는 paper 출력이므로 그 결과를 paper_v2의 성능으로 보고하면 안 된다.

## 다음 검증의 우선순위

- 기존 상태 묶음에서 paper/v2를 반복 호출하고 raw→sanitized 수정 항목을 기록한다.
  살아 있는 진영/타입, 단독 생존 focus, weight 범위는 자동 측정할 수 있다.
- actionable preference coverage를 availability와 교차해 측정한다. 선호 token 존재율과
  실제로 Q 선택을 바꿀 수 있는 비율을 구분한다.
- 조건부 카이팅은 prompt만으로 구현할 수 없다. 먼저 '조건 없는 이동 선호 생략' 대조로
  해악을 확인하고, 필요할 때 HP/거리/cooldown 조건을 표현하는 스키마와 관측을 함께 설계한다.
- protect_type의 탱킹 억제, retreat의 전투 회피 효과를 외부 return·교전·사망으로 확인한다.
- 현재 soft fixed/RSVP는 동일 paper·채널로 끝까지 비교한다. prompt 교체와 스케줄러 변경을
  한 비교에 동시에 넣지 않는다. 실험 추가나 기존 런 변경은 이번 검토에서 하지 않았다.
